# 蓝队防守手册（插件视角）

> 蓝队项目（side=defense）与红队项目平行：独立目录、独立事实库、独立工作区。蓝队不读红队的库，红队也读不到蓝队的。对抗在现实里发生，插件负责把防守动作、告警链路、处置时效记成可评分的账。
>
> **实现层以 [blueteam-design.md](blueteam-design.md) 为准**：本文是业务基准（为什么防、防什么）；设计稿负责表结构、状态机、工具、页签与校验。第 10 节的映射表是早期计划，字段名与目录以设计稿为准。

## 1. 防守方为什么有优势

| 优势 | 具体体现 | 落到插件里 |
| --- | --- | --- |
| 有主机权限 | 能登服务器看进程、看文件、看计划任务 | 资产与主机快照、进程/账号清点 |
| 有日志与流量 | EDR/NDR/WAF/系统日志/流量镜像 | 告警源（alert.source） |
| 有封禁与下线权 | 能封 IP、隔离主机、改密、下架服务 | 处置动作（response_action） |
| 有时间 | 红队限时，蓝队可以慢慢查 | MTTD/MTTR 只在蓝队侧计 |
| 有业务上下文 | 知道哪个是核心系统 | 资产名单与权重（asset.criticality） |

蓝队的真正约束不是能力，而是**不能自伤**：误封核心业务、误删生产数据、误改配置，比被红队拿分更严重。所以蓝队的所有高危动作都要走「变更审批 + 回滚预案」。

## 2. 防守五阶段（项目生命周期）

```
① 资产清点   知道要守什么：资产、暴露面、责任人、权重
② 基线加固   把明显的门关上：弱口令、开放端口、补丁、配置
③ 检测建设   看得见才有得打：日志接入、规则、告警分级、蜜罐
④ 告警研判   把噪声变成事件：分级、去重、关联、定性
⑤ 处置溯源   止血 + 清源 + 复盘：隔离、封禁、改密、取证、整改
```

每个阶段都有可量化的产出，蓝队得分就来自这些产出，而不是「我感觉防住了」。
### 2.1 基线核查清单（② 基线加固的具体项）

| 类别 | 检查项 | 合格标准 |
| --- | --- | --- |
| 账号 | 默认口令、共享账号、长期未登录、多余管理员 | 无默认口令；管理员双因素；90 天未登录禁用 |
| 端口 | 对外开放端口与业务不符、管理端口暴露公网 | 仅业务端口开放；22/3389/数据库不对公网 |
| 补丁 | 高危漏洞未修（可被公开 EXP 打） | 高危 7 天内、严重 72 小时内 |
| 配置 | 目录浏览、调试接口、弱加密协议、默认页面 | 关闭调试与目录浏览；TLS1.2+ |
| 日志 | 关键系统无日志、日志不集中、留存不足 | 主机+应用+网络日志接入 SIEM，留存 ≥180 天 |
| 备份 | 无离线备份、备份可被同账号删除 | 3-2-1 备份；备份账号与生产隔离 |

基线不是一次性动作：每次事件后都要回看「这条路径上的基线为什么没守住」。

## 3. 告警是怎么来的（蓝队核心）

### 3.1 数据源清单

| 层 | 典型来源 | 能发现什么 |
| --- | --- | --- |
| 网络 | 防火墙、NDR/IDS、DNS 日志、代理日志 | 扫描、隧道、C2 回连、异常外联 |
| 主机 | EDR、Sysmon、auditd、Windows 安全日志 | 进程创建、提权、凭据转储、持久化 |
| 应用 | WAF、Web 访问日志、中间件日志 | WebShell、注入、反序列化、异常上传 |
| 账号 | AD/域控日志、VPN、堡垒机 | 异常登录、暴力破解、黄金票据 |
| 蜜罐 | 仿真服务、诱饵文件、蜜标 | 高置信度的入侵意图 |

### 3.2 告警生成的四类规则

1. **特征匹配**：已知恶意 IP/域名/哈希、WebShell 特征、常见漏洞路径。
2. **行为基线**：偏离日常的进程链（如 `w3wp.exe → cmd.exe → whoami`）、异常父进程、异常登录时间。
3. **阈值与频次**：单位时间内的 404 激增、登录失败激增、外连次数异常。
4. **情报与蜜标**：蜜罐被访问、诱饵文件被打开——这类告警误报极低，优先级最高。

### 3.3 实时性怎么做

| 模式 | 延迟 | 适用 |
| --- | --- | --- |
| 流式（SIEM/EDR 实时推送） | 秒级 | 护网实战、真实防守 |
| 准实时（1 分钟聚合） | 分钟级 | 大多数企业 SOC |
| 批处理（小时级） | 小时级 | 日常巡检、复盘 |

插件里的实时告警通道：`/redteam/api/events` 的 SSE 推送 + 15 秒兜底轮询。蓝队侧同构，但事件类型换成 `alert` / `incident` / `action`。

### 3.4 告警分级与降噪

```
P0 已确认入侵（蜜罐命中 / 主机出现 WebShell）  → 立即响应，5 分钟内
P1 高置信可疑（异常外联 / 提权行为）          → 15 分钟内研判
P2 中置信（扫描 / 暴力破解 / 可疑上传）        → 1 小时内研判
P3 低置信（单次失败 / 情报命中但无行为）        → 当日归档
```

降噪三招：同源聚合（同一 IP 的多条告警合并）、白名单（已知扫描器/监控）、抑制窗口（同一规则 10 分钟内不重复弹）。

## 4. 名单体系（蓝队的作战地图）

| 名单 | 内容 | 用途 |
| --- | --- | --- |
| 资产名单 | IP/域名/系统/责任人/权重 | 决定先守谁 |
| 白名单 | 已知扫描器、监控、合作方 IP | 降噪，避免误判 |
| 黑名单 | 攻击者 IP、恶意域名、哈希 | 封禁与回溯 |
| 画像名单 | 攻击者 TTP、常用工具、基础设施 | 溯源与反制 |
| 变更名单 | 近期上线/改配的系统 | 解释异常，避免误封 |

名单不是静态表，每次事件后都要更新：新发现的资产进资产名单，确认的攻击 IP 进黑名单。

## 5. 与红队交战（防守动作）

红队进来之后的动作顺序，蓝队要做的是**比它快一步**：

| 红队动作 | 蓝队可观测信号 | 蓝队动作 |
| --- | --- | --- |
| 端口/目录扫描 | WAF/IDS 大量 404、连接数激增 | 限速、封 IP、加规则 |
| 漏洞利用 | 异常请求体、命令回显、进程链异常 | 隔离主机、下架服务、打补丁 |
| WebShell 落地 | 新增 .jsp/.php 文件、异常进程 | 删马、改密、查入口 |
| 隧道建立 | 异常长连接、DNS 隧道特征 | 断连、封目标端口、查跳板 |
| 凭据转储 | lsass 访问、SAM 读取 | 强制改密、吊销票据、查横向 |
| 横向移动 | 内网 SMB/WinRM 异常 | 分段隔离、关共享、查账号 |

**诱捕与反制**（可选，风险自负）：蜜罐、蜜标、假凭据。反制的前提是有明确授权与法律边界，插件只记录动作与证据，不做自动反制。

### 不能自杀：自伤约束

蓝队三类动作必须走审批，且计入扣分：

1. **误封**：封了核心业务或合作方 IP → 每次扣分，并要求 30 分钟内恢复。
2. **误删/误改**：删了生产文件、改了关键配置 → 扣分，且必须留回滚记录。
3. **过度处置**：为了「稳」直接下线整台服务器 → 按业务影响扣分。

插件的做法：`response_action` 里带 `impact`（影响面）与 `rollback`（回滚方式），没有回滚预案的高危动作不允许提交。

## 6. 积分规则（蓝队版）

| 维度 | 指标 | 计分思路 |
| --- | --- | --- |
| 检测覆盖 | 覆盖的 ATT&CK 技术数 / 关键 TTP 数 | 每覆盖 +N，关键 TTP 加权 |
| 发现时效 | MTTD | <15min 满分，2h 归零 |
| 处置时效 | MTTR | <30min 满分，4h 归零 |
| 暴露面收敛 | 高危端口/弱口令/未打补丁的收敛数 | 每项 +N |
| 误报 | 误报数 / 总告警数 | 每次 −M |
| 自伤 | 误封/误删/过度处置 | 每次扣分 + 必须恢复 |
| 漏报 | 红队达成但蓝队无记录 | 按对应红队得分比例扣 |

与红队的区别：红队按「拿到什么」计分，蓝队按「守住什么 + 多快发现」计分。

## 7. 蓝队智能体设计

| 角色 | 职责 | 主要工具 |
| --- | --- | --- |
| soc-lead 值守指挥 | 分级、派活、对外汇报 | alert_query / incident_open / digest |
| asset-owner 资产与暴露面 | 资产清点、暴露面收敛 | asset_import / exposure_query |
| detection 检测工程 | 写规则、接日志、覆盖矩阵 | detection_add / detection_matrix |
| triage 告警研判 | 真警/误报、关联、定性 | alert_triage / incident_link |
| responder 处置响应 | 隔离、封禁、改密、取证 | contain / eradicate / evidence |

主会话同样是「指挥 + 派活」，子智能体是叶子节点。每条告警必须有结论（真/假/待查），每个事件必须有时间线。

## 8. 数据模型（落在项目库里）

```
asset            复用：资产清点（source = cmdb/passive/log）
exposure         暴露面：端口/服务/弱口令/未打补丁
alert            告警：source/rule/severity/entity/status
incident         事件：detected_at / contained_at / eradicated_at
response_action  处置：kind/target/impact/rollback/operator/at
detection        检测规则：ttp/product/scope/content/verified
```

MTTD = incident.detected_at − alert.first_seen；MTTR = incident.contained_at − incident.detected_at。

## 9. 报告（蓝队交付物）

1. 防守态势：资产数、暴露面收敛率、覆盖的 TTP 数。
2. 事件清单：时间线、定性、处置、影响、回滚。
3. 检测覆盖矩阵：ATT&CK × 有无日志/告警/规则。
4. 整改清单：按风险排序，带责任人与期限。
5. 误报与自伤记录：诚实列出，这是下一个周期要优化的地方。
